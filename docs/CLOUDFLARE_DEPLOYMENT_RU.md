# Развёртывание MIRRAI SaaS на Cloudflare

Это руководство относится к серверному приложению. Публичные статические демо
остаются отдельными Cloudflare Pages-проектами и продолжают публиковаться через
`MIRRAI CI`.

## Что автоматизировано в репозитории

- `npm run deploy:saas` собирает конфигурацию Worker из переменных окружения,
  применяет SQL-миграции к D1, публикует приложение и загружает настроенные
  секреты в Worker.
- `.github/workflows/deploy-saas.yml` запускается вручную только из `main` и
  публикует только в `mirrai-staging` GitHub Environment. Production намеренно
  недоступен в workflow, пока не согласованы платное хранилище и миграция данных.
- Сборка Cloudflare не добавляет упаковщик OpenAI Sites. Обычная сборка
  существующего приложения и Pages-демо сохраняют прежнее поведение.
- Очередь генерации читает `MIRRAI_APP_ORIGIN`; пока переменная не задана,
  расписание продолжает обращаться к прежнему приложению.

## Бесплатное staging-окружение

Для staging используется Workers Free + D1 + KV, без оформления R2-подписки.
Создать отдельные ресурсы, не используя D1/KV/R2 статических демо:

| Среда | D1 database | Object storage |
|---|---|---|
| staging | `mirrai-saas-staging` | KV namespace `mirrai-saas-staging` |
| production | `mirrai-saas-production` | R2 bucket `mirrai-saas-production` (пока не включать без отдельного решения о биллинге) |

Скопировать UUID D1 и ID KV namespace для staging. KV бесплатного тарифа
ограничен 1 GB storage и 25 MiB на значение; приложение ограничивает один
загружаемый объект 24 MiB. Бесплатные квоты KV — 100 000 чтений и 1 000 записей
в день; при превышении операции будут недоступны до сброса квоты. R2 остаётся
целевым storage для production и больших моделей, но требует включить подписку
с оплатой сверх бесплатного usage. Пустая D1 будет заполнена миграциями из
`drizzle/`; существующая база приложения на прежнем хостинге автоматически не
копируется.

Создать отдельный Cloudflare API token для Workers, не расширяя токен
`CLOUDFLARE_API_TOKEN`, который используется Pages-демо. Токену нужны только
права на выбранный аккаунт для публикации Worker, изменения D1 и загрузки
Worker secrets; доступ к остальным аккаунтам не нужен.

## GitHub настройки

В Settings → Environments использовать отдельную среду `mirrai-staging` и задать
переменные:

- `CLOUDFLARE_ACCOUNT_ID` — аккаунт MIRRAI;
- `MIRRAI_D1_DATABASE_ID` — UUID соответствующей D1;
- `MIRRAI_STORAGE_MODE` — `kv` для бесплатного staging;
- `MIRRAI_KV_NAMESPACE_ID` — ID KV namespace staging;
- `MIRRAI_R2_BUCKET_NAME` — только для R2 окружения;
- `MIRRAI_APP_ORIGIN` — канонический HTTPS origin Worker или домена;
- `MIRRAI_OPERATOR_EMAIL` — почта владельца платформы, с которой он войдёт;
- `MAIL_FROM` — подтверждённый отправитель писем.
- `RECONSTRUCTION_API_URL` — необязательный HTTPS URL собственного шлюза генерации;
- `HUGGINGFACE_SPACE_URL` — необязательный HTTPS URL Space с Hunyuan3D-2.1 или совместимым API.

В каждой среде создать secrets:

- `CLOUDFLARE_WORKERS_API_TOKEN` — отдельный токен Worker/D1;
- `RESEND_API_KEY` — ключ отправки писем для подтверждения почты и сброса пароля.
- `RECONSTRUCTION_API_TOKEN` — токен собственного шлюза, если он используется;
- `HUGGINGFACE_TOKEN` — токен доступа к закрытому Hugging Face Space, если он используется.

`GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` необязательны: Google-вход включится
после их добавления. Redirect URI должен совпадать с
`<MIRRAI_APP_ORIGIN>/api/auth/google/callback`.

Если URL сервиса генерации не задан, приложение и кабинет могут работать, но
очередь не сможет отправлять задания на построение 3D. URL передаются в Worker
как переменные окружения, токены — только как Worker secrets; браузеру они не
публикуются. Наличие ссылки на Hugging Face Space само по себе не означает, что
Space запущен, имеет GPU-квоту или доступен на бесплатном тарифе.

Для публичного запуска почтовый отправитель должен быть подтверждён у почтового
провайдера, иначе пользователи не смогут завершить подтверждение почты и
восстановление доступа. Полноценный платёжный провайдер на этом этапе ещё не
подключён.

## Первый staging запуск

После создания ресурсов и GitHub Environment открыть Actions → **Deploy MIRRAI
SaaS** → Run workflow. Workflow публикует только в `staging`. После завершения проверить вход,
подтверждение почты, восстановление пароля, создание магазина, загрузку файла,
изоляцию магазина, установку виджета и события. `MIRRAI_APP_ORIGIN` в настройках
GitHub Environment задаёт адрес самого staging Worker. Отдельная переменная
репозитория `MIRRAI_APP_ORIGIN` управляет scheduled generation queue; она пока
не переводится на staging автоматически. Менять её можно только после проверки
этого Worker и очереди, чтобы не перенаправить действующую генерацию на
непроверенную среду.

Production сейчас не развёртывается: он требует отдельного storage-плана,
резервного копирования и проверки восстановления базы. После успешного staging
нужно отдельно согласовать этот план. Миграции выполняются перед публикацией;
для будущих несовместимых изменений использовать expand/contract, чтобы старая
версия Worker не сломалась во время обновления схемы.

## Текущие ограничения

- Этот workflow пока не запускался: staging D1/KV и базовые GitHub variables
  созданы. Нужны deploy-токен, почтовый provider/секреты, `MIRRAI_OPERATOR_EMAIL`
  и `MAIL_FROM`.
- База, загрузки, пользователи и секреты предыдущего размещения не переносятся
  автоматически.
- Google OAuth, письма и оплата подтверждаются только после подключения реальных
  credentials и проверки в staging.
- Для генерации нужны отдельно настроенный GPU-шлюз/Space и проверка полного
  цикла заявки; этот workflow передаёт его настройки, но не создаёт GPU-сервис.
- Static demo CI не является проверкой SaaS deployment.

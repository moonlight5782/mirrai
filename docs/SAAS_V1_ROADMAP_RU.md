# План выпуска MIRRAI SaaS v1

Этот документ фиксирует путь от презентационного демо к первому платному
подключению мебельного магазина. Демо и SaaS — разные развертывания: публичные
демо на Cloudflare Pages доступны, кабинет и серверный продукт пока не
опубликованы как производственный сервис.

## Текущее состояние

- **Демо:** два публичных статических каталога, по 16 товаров и моделей.
- **Код кабинета:** есть регистрация и вход по паролю, восстановление доступа,
  Google OAuth, создание магазина, управление каталогом и файлами, админские
  страницы, события виджета, аналитика, установка и очередь генерации.
- **Авторизация:** `getChatGPTUser` уже совместим с сессией MIRRAI; это имя
  адаптера, а не обязательный вход через аккаунт ChatGPT.
- **Развертывание:** GitHub Actions публикует статические демо. Добавлен
  воспроизводимый, запускаемый вручную Cloudflare Worker deployment workflow;
  он ещё не запускался. D1/R2, домен и secrets для SaaS не настроены.
- **Оплата:** checkout и webhooks отсутствуют; срок подписки управляется
  оператором.
- **Google-вход:** код есть, но для реального OAuth нужны Client ID/Secret и
  настройки домена.
- **Модели:** загрузка и статусы каталога предусмотрены; создание качественной
  модели по фото требует GPU и проверки человеком перед публикацией.

## План и критерии выхода

### 1. Производственный контур

Развернуть полное приложение на Cloudflare Workers под одним основным адресом;
оставить статические демо на их Pages-ссылках. Создать отдельные production и
staging D1/R2, применить миграции, настроить домен, секреты, резервные копии,
логи и автоматическую публикацию после CI.

**Готово, когда:** основной URL ведёт на серверное приложение, данные сохраняются
между входами, можно откатить deployment, а оба демо по-прежнему доступны.

### 2. Сквозной процесс магазина

Регистрация/вход → создание магазина → импорт CSV или добавление товара → загрузка
модели либо фотографий и размеров → заявка на расчёт → статусы → проверка и
публикация модели оператором. Проверить права на каждой странице и API; владелец
видит только свои магазины. Первый пилот сопровождать вручную: не обещать
автоматический разбор любого сайта или безошибочную генерацию по фото.

**Готово, когда:** новый клиент входит без ChatGPT, чужой магазин недоступен даже
через прямой API-запрос, оператор может обработать заявку и опубликовать модель,
ошибки не теряют загруженные файлы.

### 3. Установка виджета

Выдать каждому магазину публичный идентификатор и готовый код установки. Для
пилота поддержать универсальный скрипт и сопоставление по SKU; следующий
платформенный коннектор выбрать по первому реальному клиенту. Добавить проверку
установки, домена, подписки, вариантов цвета и понятный fallback без модели/AR.

**Готово, когда:** установку можно выполнить по короткой инструкции, виджет
появляется у сопоставленного товара и не ломает карточку или корзину. Секретный
серверный ключ не помещается в клиентский код магазина.

### 4. Статистика и эксплуатация

Показывать владельцу события виджета и период, оператору — магазины, каталоги,
подписки и ошибки. Развести определения: показ кнопки, открытие 3D, запрос AR.
Запуск AR не считать доказательством размещения предмета в комнате. Для связи с
покупками потребуется интеграция заказов.

**Готово, когда:** события привязаны к правильному магазину, дубли контролируются,
период и часовой пояс понятны, ошибки загрузок и виджета заметны оператору.

### 5. Подписка и оплата

Зафиксировать тарифы: подготовка моделей отдельно от ежемесячной работы виджета.
Добавить checkout, подтверждаемые webhook-события, историю платежей,
продление/отмену и автоматическое изменение доступа после подтверждения оплаты.
Секреты провайдера хранить только на сервере.

Для реального checkout нужен провайдер, работающий с бизнесом в Молдове, и
оформленный продавец. У основателя пока нет ИП/компании, поэтому этот этап нельзя
закрыть только программированием. До оформления пилот можно вести по
согласованному счёту вручную, не показывая фиктивную оплату.

**Готово, когда:** платежи проходят полный цикл; webhook идемпотентен; браузер не
может сам активировать подписку; отказ/возврат корректно меняет доступ; счет и
срок видны владельцу.

### 6. Ограниченный запуск

Подключить один магазин, затем второй. На каждом проверить товары, варианты,
виджет, iPhone Safari, Android Chrome и встроенный браузер. Исправить блокирующие
проблемы и только после пилотов включать самостоятельную регистрацию и продажи.

**Критерий готовности SaaS:** клиент сам регистрируется, создаёт магазин,
добавляет каталог, видит стоимость, оплачивает, устанавливает виджет, проверяет
его, смотрит статистику и управляет продлением; оператор поддерживает его из
защищённой админки.

## Следующие действия

1. Создать отдельные Cloudflare D1/R2 для staging и production, добавить
   GitHub Environments/secrets и впервые развернуть staging по
   [`CLOUDFLARE_DEPLOYMENT_RU.md`](CLOUDFLARE_DEPLOYMENT_RU.md).
2. Проверить опубликованные регистрацию, кабинет и изоляцию ролей/магазинов.
3. Закрыть путь «каталог → проверка модели → публикация».
4. Сделать установку виджета воспроизводимой и проверяемой.
5. Подключить статистику и мониторинг.
6. Подключить платежи, когда определены продавец и провайдер.
7. Провести пилоты; затем открыть самостоятельную коммерческую регистрацию.

## Не считать завершением

- Наличие страницы или кнопки без работающего серверного сценария.
- Успешную сборку вместо проверки опубликованного приложения.
- Статическое демо вместо кабинета и базы.
- Ссылку на GLB вместо проверки масштаба, материалов и геометрии.
- Запрос AR вместо подтверждения размещения модели.
- Ручное выставление срока вместо автоматического платежного цикла.
